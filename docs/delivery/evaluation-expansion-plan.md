# Expanding the evaluation — what was done, and what cannot be

The current measurement rests on **5 scored dev cases, 24 reviews, one annotator**. That was
enough to fail a gate decisively — the failure is large and consistent across cases — and it is
not enough to characterise a model or support any published accuracy claim.

This records what expansion is genuinely possible, what was done, and the one part that
**cannot** be done by the person who wrote the questions.

---

## What cannot be done here, and why saying so matters

**A second annotator must be a different person.** The golden set's questions and its relevance
labels were produced by the same author. Re-labelling by that author, or by a tool the author
directs, produces *the same judgement wearing a second hat* — it would raise the apparent rigour
while measuring nothing new, which is worse than the current honest state.

The same applies to an "independent" second pass generated by an AI assistant working from the
same instructions: it inherits the framing that produced the original labels. Reporting that as
inter-annotator agreement would be a fabricated control, and this project's whole argument is
against exactly that.

**So ASM-05 stays open.** It requires a human who did not write the questions. The labelling
packet below exists to make that person's job 30 minutes rather than a day.

## Labelling packet — ready for a second annotator

Give the annotator only:

1. The 24 review texts with their ids, **no ratings, no metadata** — metadata leaks the intended
   grouping.
2. The 14 questions, **without** the existing `relevant_ids` or `rationale` fields.
3. One instruction: *"For each question, list every review a product manager would accept as
   direct evidence. Include partial matches. When unsure, include it and mark it uncertain."*

Then compute Cohen's kappa against the existing labels and adjudicate every disagreement in
writing.

### The three calls most likely to be rejected

These were judgement calls, and a second reader may reasonably decide otherwise. **VAL-016**
drives all three — a review that says login is broken *but* the interface is easy once inside:

| Case | The call | Why it is contestable |
| --- | --- | --- |
| D1 "locked out of their accounts" | VAL-016 **excluded** | They report broken login but do get inside. Is that "locked out"? |
| D4 "happy with signing in" | VAL-016 **excluded** | Positive about the interface, negative about login |
| H5 "praise how the app looks and feels" | VAL-016 **included** | Included here for interface praise while excluded above — arguably inconsistent |

If the second annotator flips VAL-016, several metrics move. That single review is the most
informative disagreement available, which is why it is flagged rather than hidden.

## Corpus size — what a larger dataset would and would not fix

At 24 reviews, one label flip moves recall@5 by roughly 7 points. That is the dominant source
of uncertainty, and it is why **no confidence interval is reported** anywhere in this project.

However — and this is the part worth being clear about — **a larger corpus would not change the
current conclusion.** The semantic failure is not marginal:

| | Measured | Bar |
| --- | --- | --- |
| recall@5 | 0.267 | 0.70 |
| absent-topic FP | 0.50 | 0.25 |
| Thresholds clearing the gate | **0 of 66** | ≥ 1 |

The signal/noise overlap is structural: the weakest correct answer scores **0.1774** while the
strongest pure false positive scores **0.3040**. More data would sharpen that estimate, not
reverse it. Expanding the corpus *before* testing a stronger model would be measuring the same
failure more precisely — motion, not progress.

**So the order is: fix the model first, then expand the corpus to measure the candidate that
actually looks viable.** Expanding now would be expensive diligence theatre.

## Holdout status

**The holdout split has not been run, and must not be.** Seven cases (H1–H7) remain untouched.

The harness enforces this: `--holdout` refuses without `--confirm`, and every run appends to
`eval/holdout-runs.log`. That file is currently **absent**, which is the correct state — it is
the evidence that the holdout is still clean.

It should be run once, on a candidate that has already cleared the dev split. Running it now, on
a configuration known to fail, would burn the only independent measurement available for nothing.

## Ordered plan

| # | Step | Why this order | Status |
| --- | --- | --- | --- |
| 1 | Test fp32 MiniLM-L6 | Separates quantisation damage from model capacity. One-line harness change, minutes to run | **Next** |
| 2 | If fp32 insufficient, test a larger embedding model | Capacity is the next hypothesis after quantisation | Blocked on 1 |
| 3 | Hybrid lexical + semantic | The failure modes are complementary: lexical is perfect on absent topics, semantic is perfect on D2 | Blocked on 1–2 |
| 4 | Second annotator on the current 14 questions | Cheap, and validates the instrument before the corpus grows | **Can start now — needs a person** |
| 5 | Expand corpus to 150–300 reviews, 40+ questions | Only worth doing for a candidate that has cleared dev | Blocked on 1–3 |
| 6 | Holdout run, once | The release measurement | Blocked on all above |

Steps 1 and 4 are independent and can run in parallel. Everything else is sequential, and
attempting step 5 before step 1 is the most likely way to waste a week.

## What would make me abandon the feature

If fp32 does not lift recall@5 above **0.50**, the gap to 0.70 is not a tuning problem and the
honest call is to cut the on-device mode and keep lexical retrieval.
[DEC-03](decision-log.md) was recorded as a two-way door for exactly this outcome. The measured
gain over lexical today is **0.067 recall**, bought with a 1.7 MB download, a CDN dependency,
device storage, and a false-positive rate twice the agreed ceiling. On current evidence that
trade is not worth making.
